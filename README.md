# WWF Solver

Takes an image of a Words With Friends game screen, reconstructs the board and rack, and
returns the highest-scoring legal moves. Built milestone by milestone from the build spec.

**Full guide: [docs/usage.md](docs/usage.md)** covers installing, the board and move model,
scoring and validation, solvers and their parameters, choosing a dictionary, configuration, tests,
and extending the code.

## Running

```sh
uv sync
uv run wwf-serve              # http://127.0.0.1:8000 ; add --host 0.0.0.0 to use it from a phone
```

API docs are at `/docs` while it runs.

## Development

```sh
uv sync                 # create .venv and install everything (add --extra train for PyTorch)
uv run pytest           # fast tests; add -m "" to include tests marked slow
uv run ruff check . && uv run ruff format --check .
uv run mypy             # strict on wwf.core and wwf.solvers
uv run lint-imports     # enforces core <- {vision, solvers} <- api layering
```

Config lives in `config/` (board layout, letter values, solver registry); the default word list is
`assets/dictionaries/words.txt` (ENABLE1 is the alternative). The trie is cached in `.cache/` keyed by the word list's hash.
Set `WWF_ROOT` to point at a different directory holding `config/` and `assets/`.

**Choosing a dictionary.** `config/dictionaries.json` lists the selectable word lists and the
default (`words`, i.e. `words.txt`; `enable1` is the alternative). Any other `.txt` file dropped into
`assets/dictionaries/` is offered automatically under its file name. Set `WWF_DICTIONARY=words`
to change the default without editing config. In code, `default_dictionary_registry().get(id)`
returns the chosen dictionary (loaded on first use, then cached); the API (M5) will take a
`dictionary_id` alongside `solver_id`, and the Options page (M6) will show it as a dropdown.

**Dictionary caveat.** The WWF dictionary is proprietary, so no list matches it exactly.
`words.txt` is the default because it covers words seen in real games that ENABLE1 lacks (DA,
NESH, SHEN, GI, ROSA, JE), but it still misses some (DUH) and may accept words WWF rejects.
Any newline-separated word list can be swapped in.

## Milestone notes

**M1, scaffold and core.** `wwf.core` holds the immutable domain model: `Board`, `Tile`,
`Bonus`, `Rack`, `Move`/`Placement` (with `build_move` to derive direction, main word and start
from a set of placements), `score_move` and `validate_move` (named violations), the trie
dictionary with its pickle cache, and the validated `BoardConfig` loader for
`config/wwf_classic.json`. Tests cover the worked scoring examples (HELLO first move, a blank on a
triple word, a 7-tile bingo, parallel plays, stacked word bonuses), every named violation, a
Hypothesis transpose-invariance property for scoring, and config rejection of malformed layouts.
`validate_move` takes an optional `rack` argument beyond the spec signature, needed for
`tile_not_in_rack`.

**M2, solvers.** `wwf.solvers` has the plugin protocol (`base.py`: `SolverParam`, `ScoredMove`,
`SolverResult`, `resolve_params` which raises `ParamError` on bad input), the registry (discovers
solver classes in the package and cross-checks `config/solvers.json`: an enabled id with no
implementation fails startup, disabled ids without code are listed as planned), and two solvers.
`anchor_trie` ("Smart brute force") is Appel-Jacobson anchors, cross-checks and left/right
extension over the trie, with down moves generated by transposing the board. It ranks every
candidate with `core.scoring.score_raw` (an allocation-free total that shares the core scoring
rules) and builds full `score_move` breakdowns only for the returned moves plus ties at the
cutoff. `dummy_random` is the clearly labelled demo. `tests/solvers/reference.py` is a slow
brute-force generator; the equivalence test checks that `anchor_trie` finds exactly the same legal
move set and scores on 20 random boards (0-32 tiles, 50-716 legal moves each, 4 with a blank).
Performance: a 68-tile mid-game board with `AEIRST?` (~12k legal moves) solved in 400-430 ms of
CPU time on an M5 Pro measured under heavy machine load (load average ~17), so expect less on an
idle machine; two blanks took about 1.4 s. The slow-marked test enforces the 500 ms bar.
`load_dictionary` calls `gc.freeze()` because the garbage collector rescanning the ~390k trie nodes
otherwise doubles solve time.

### Adding a solver

Drop a module in `src/wwf/solvers/` with a class that has `id`, `display_name`, `description`,
`params` (a tuple of `SolverParam`) and `solve(board, rack, dictionary, cfg, **params)`, then add
`{"id": "<your id>", "enabled": true}` to `config/solvers.json`. Call `resolve_params` at the top
of `solve` and score with `wwf.core.scoring`; do not reimplement scoring.

**M5 and M6, API and web pages (built ahead of M3-4 at the owner's request).** `wwf.api` is a
FastAPI app (`create_app`, started by `wwf-serve`) with in-memory sessions (30-minute sliding TTL,
swept every minute), all spec routes, and a few additions:
- `POST /session`, which starts an empty session for typing a board in
- `GET /session/{id}/image`
- `GET /dictionaries`, plus a `dictionary_id` alongside `solver_id` in options and solve calls
- the score in the `/validate` response when a move is legal

Recognition and solving run in a thread pool. Solves time out after 10 s with a 504 and
`partial: true`; solvers can't be interrupted, so no moves come back. Request ids are on every
response, in the `X-Request-ID` header and in the log. `GET /solvers` returns
`{request_id, default_id, solvers: [...]}` rather than a bare array, so it can carry the request id.

`wwf.web` holds the Jinja2 templates, CSS, `app.js` (about 200 lines) and vendored HTMX. Every
form is a plain POST, so the pages work without JavaScript; options persist in a cookie and are
mirrored to `localStorage`. Until vision exists, uploads are stored and shown, but recognition
returns an empty board with the warning `recognition_unavailable`.

Verification: tests in `tests/api` cover the API and drive the pages as a no-JS browser. The
review grid's keyboard flow was checked by driving headless Chrome, and the layouts were checked
by screenshot at 390 px and 1280 px. Not yet verified on a real phone or against a Docker build.

**Camera first.** The upload page leads with **Take a photo of the board**. On phones that opens
the camera app (`capture="environment"`); on computers with a webcam it opens an in-page
viewfinder, where the browser allows it (localhost or https). Uploading a screenshot and typing a
board in are the second and third options. Pictures are scaled in the browser to 2000 px on the
long side before upload, and the Review page offers **Retake photo** before **Upload instead**.
Checked in headless Chrome with a fake webcam and with phone touch emulation.

**Fixture collection.** `wwf-serve --collect-fixtures` saves every picture taken or uploaded into
`assets/fixtures/` and loops back to the camera, so you can take many in a row. The `/fixtures`
page lists them and opens each one in the review grid; **Save label** writes `<name>.json` with
the true board and rack. See "Collecting test pictures" in `docs/usage.md`.

**Real layout and dictionary.** The owner's photos showed the current WWF app uses a different
bonus layout from the spec's, in rows 2-7 and their mirrors. It is now `config/wwf_current.json`
and the default; the spec's layout is kept as `config/wwf_classic.json`, selectable with
`WWF_BOARD_CONFIG`. At the owner's choice, `words.txt` replaced ENABLE1 as the default dictionary.

**M3-M4, first board reader (photo path).** Built from the owner's labelled photos instead of the
spec's screenshot-first plan, because the camera is the main input. It differs from the spec in
three ways:
- The board is found by matching the coloured bonus squares to the layout (Hough-style voting,
  then a RANSAC homography), not by projection profiles or phone-screen detection.
- Occupancy is a colour rule that uses the known layout.
- Letters are a nearest-neighbour template matcher on HOG features (the spec's template-matcher
  baseline), with real crops plus font-rendered letters. There is no CNN/ONNX model yet.

Results:
- On boards held out of training: 98.2% of squares right, most errors flagged for review.
- On an unseen game: 224-225/225 squares and all racks right, about 0.2 s per photo.

In collection mode new pictures become draft labels automatically, and saving a label retrains
the reader in the background. Not yet done: screenshots tested, other phone shapes, the CNN.
